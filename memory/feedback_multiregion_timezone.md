---
name: 해외 접속 가능한 서비스의 TZ 전제
description: 해외에서도 쓰는 서비스는 날짜/시간 설계에서 "서버 TZ = 사용자 TZ" 전제를 쓰면 안 된다
type: feedback
---
해외에서도 접속 가능한 서비스라면, 날짜/시간을 다루는 설계·리뷰에서 "프론트는 항상 서버 TZ 기준 Y-m-d" 같은 단순 가정을 쓰면 안 된다.

**Why:** 해외 사용자가 자기 로컬 달력으로 날짜를 고르면 그건 서버 TZ 기준 날짜가 아니다. 서버가 일괄 자기 TZ 자정으로 해석하면 해외 사용자에겐 하루가 어긋난 결과가 나간다. 사용자 프로필에 TZ 설정 필드가 존재한다면 그 자체가 이 전제가 깨진다는 신호다.

**How to apply:**
- 날짜 입력 파라미터(startDate/endDate 등) 설계 시 "서버 TZ = 사용자 TZ" 전제 금지. 요청자 TZ 를 헤더 또는 세션/프로필에서 얻어 명시적으로 해석한다 (예: `new DateTime($v, new DateTimeZone($userTz))`).
- TZ 인자를 생략한 파싱(`new DateTime($v)`, `formatToIso8601($v)`)은 서버 설정에 묵시 의존하므로 해외 접속에선 부정확 — 제안 시 TZ 인자 명시를 강제한다.
- 단, PR 스코프가 좁을 땐 "해외 TZ 처리"는 별건 티켓으로 분리하고 현 PR 은 형식 검증 정도만 손대는 것이 현실적.
- DB 저장이 UTC epoch 인지 서버 로컬인지부터 확인해야 TZ 변환 로직이 의미가 있다.
