리서치·분석 문서는 핵심만 짧게. 표 남발·가상 시나리오(서버 TZ 3가지 경우 등) 분기 설명·이론적 분류법은 줄인다.

**Why:** 실제 피드백에서 "너무 어렵게 썼다"는 지적이 나왔다. 사용자는 현업 백엔드 개발자이고, 조사 결과는 판단 근거로 쓰이므로 **결론 + 고쳐야 할 file:line 목록 + 한두 문장 이유**면 충분하다. 배경 설명을 반복하거나 언어 동작 원리를 풀어쓰면 가독성이 떨어진다.

**How to apply:**
- 결론을 맨 위에 한두 줄로. 긴 ~85% 같은 확률 표현 지양.
- "시나리오 1/2/3" 분기 서술 금지. 대표 케이스 하나 + "이 조건 만족 안 하면 깨짐" 정도.
- 표는 "고쳐야 할 지점 목록"처럼 액션 가능한 경우에만. 같은 사실을 여러 절에 다른 관점으로 반복하지 말 것.
- 코드 블록은 실제 고치거나 참조할 라인만. 동작 원리 설명용 의사코드 금지.
- 설계안은 시그니처 1~2개 + 왜 그렇게 하는지 한 줄. "트레이드오프" 절 길게 쓰지 말 것.
